\section{Introduction}
\subsection{Purpose of Testing}
Testing verifies that CCMS implements the specified competition policies and preserves them when actions are invalid or storage fails. The main objective is to validate observable behavior and invariants rather than mirror individual lines of implementation.
\subsection{Testing Scope}
The suite covers authentication, account creation, ownership and role checks, competition phases, team membership, registrations, submissions, evaluations, rankings, export, knockout progression, password storage, file locking, restart persistence, corrupt input, and failed-write rollback. Network integrations, automatic grading, multiple clients, accessibility certification, and performance benchmarks are outside the executed scope.

\section{Test Strategy}
\subsection{Unit Testing}
Direct policy checks validate the 40/35/25 project formula, score bounds, password verification and salt uniqueness, and ranking outcomes. These are executed within the same dependency-free runner as the integration scenarios.
\subsection{Integration Testing}
CampusService is exercised against a real Repository in a uniquely named build subdirectory. Most tests use an injected fixed UTC clock representing 29 October 2026; a separate clock places submission exactly at the deadline. The test dataset is isolated from the user's application database. Tests log in as distinct actors instead of passing forged role flags.

The persistence tests reopen the saved file, attempt a concurrent repository lock, supply an invalid serialized file, and deliberately obstruct the temporary save path. The failed-write case verifies that the service restores its prior team count rather than leaving an unsaved in-memory change.
\subsection{System Testing}
Complete application-service workflows cover project judging, programming results, and a knockout champion. A separate Swing suite performs 16 checks through actual controls on the event-dispatch thread, using an isolated repository. It enters credentials, clicks buttons, changes search/filter controls, creates a team, records a match winner, checks the live project total and saves its review, cancels a dialog, and checks layout at the minimum window size. These are programmatic control interactions, not operating-system mouse automation. Eight actual Swing screens were also rendered for visual inspection. A human usability study was not performed. The test runner returns a nonzero process exit code if any check fails.

\section{Test Results}
\subsection{Test Execution Summary}
Execution date: 3 November 2026. Platform: Windows. Build: portable JDK 21, Java 17 target. Result: \textbf{70 service checks and 16 Swing UI checks passed; 0 failed}. Both suites can be run with:
\begin{verbatim}
.\build-app.ps1 -Test -UiTest
\end{verbatim}
Maven integration uses two JUnit wrapper methods around the original ordered suites. Default mvn test executes 70 service checks and skips the Swing wrapper; mvn test -Pui-tests executes 70 service plus 16 Swing checks. Surefire therefore reports two wrapper tests, not 86 independent JUnit methods. A graphical session (or an appropriate virtual display on Linux) is required for Swing. The runners generate CSV results and timestamped summaries. The evidence helper copies these files to \code{docs/evidence} and generates the report tables.

\clearpage\section{Conclusion}
The suite provides executable evidence for the central OOAD behaviors: format-specific policies, protected actions, lifecycle guards, and persistence integrity. The known limits are documented and the tests can be rerun locally without an external framework. Future testing should extend GUI interaction coverage, add randomized bracket and ranking cases, and load testing before extending the application to real campus deployment.
